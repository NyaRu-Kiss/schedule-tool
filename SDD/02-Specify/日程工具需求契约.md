# WorkBuddy 日程工具需求契约

## 1. 基本信息

| 字段 | 内容 |
|------|------|
| 产品名称 | WorkBuddy 日程工具 |
| 需求类型 | MCP + Agent + 后端服务 |
| 数据库 | MySQL |
| 目标用户 | WorkBuddy 用户 |
| 当前状态 | 需求契约 |

## 2. 需求背景

现有 `schedule-tool` 支持待办记录、档期编排和定时提醒。接入 WorkBuddy 后，用户希望通过语音自然地创建日程；当用户没有明确指定开始时间时，系统应根据已有日程自动寻找空闲时间段并安排；到达提醒时间后，WorkBuddy 应主动通知用户。

## 3. 需求目标

系统需要提供一个日程 MCP，由 WorkBuddy 的固定调用流程使用。MCP 只负责连接 WorkBuddy 和日程 Agent；Agent 负责处理业务请求并调用日程后端，后端负责最终的业务校验和 MySQL 数据操作。

## 4. 用户场景

### 4.1 指定时间添加日程

用户通过语音表达“明天下午三点提醒我开会”。系统识别标题、开始时间、时长或结束时间、提醒规则，创建日程和提醒。

### 4.2 未指定时间自动排期

用户表达“明天帮我安排一小时写周报”，但没有指定开始时间。系统根据日期、可用时间范围、日程时长和已有日程，选择一个符合限制的空闲时间段并创建日程。

### 4.3 定时提醒

WorkBuddy 定时任务按固定周期调用 MCP。MCP 将请求转发给 Agent，由 Agent 从后端获取到期且未发送的提醒；WorkBuddy 发送通知，通知完成后再通过 MCP 转发确认请求。

## 5. 功能需求

### FR-001 语音日程创建

- 系统应支持 WorkBuddy 将语音转换为文本后创建日程。
- Agent 应提取标题、开始时间、结束时间或时长、提醒时间、时区等结构化参数。
- 未指定开始时间时，创建请求必须进入自动排期逻辑。
- 指定开始时间时，系统必须校验时间冲突和业务限制。
- 创建成功后返回日程 ID、最终开始时间、结束时间和提醒信息。

### FR-002 自动排期

- 系统应支持根据用户指定日期或日期范围寻找空闲时间段。
- 排期时必须考虑已有有效日程、日程时长、用户时区和业务工作时间。
- 找不到符合条件的时间段时，不得创建无时间或冲突的日程，应返回明确失败原因。
- 自动排期成功后，返回系统实际安排的时间段。

### FR-003 定时提醒

- 系统应支持为日程设置提醒时间。
- WorkBuddy 定时任务应按固定周期触发提醒查询。
- 只能返回到期、有效且未发送的提醒。
- 每条提醒发送成功后必须标记为已发送。
- 重复轮询不得导致同一提醒重复发送。
- 发送失败的提醒应保留待发送状态，以便后续重试。

### FR-004 日程数据管理

- 系统应保存日程标题、用户、开始时间、结束时间、时区、来源和状态。
- 系统应保存提醒关联的日程、用户、提醒时间、发送状态、发送时间和幂等键。
- 日程创建和提醒创建必须保持数据一致性。

### FR-005 用户反馈

- 创建成功时，WorkBuddy 应告知用户日程的最终安排时间。
- 自动排期成功时，反馈中必须明确说明这是系统安排的时间。
- 参数缺失、时间冲突、没有可用时间或提醒失败时，应返回可理解的错误信息。

## 6. MCP 能力契约

系统只有一个日程 MCP，提供以下三个能力：

| 能力 | 用途 | 调用方 |
|------|------|--------|
| `create_schedule` | 按指定时间创建日程；未指定时间时自动排期 | WorkBuddy，经 MCP 转发给日程 Agent |
| `poll_reminders` | 查询到期且未发送的提醒 | WorkBuddy 定时任务，经 MCP 转发给日程 Agent |
| `ack_reminder` | 确认提醒已发送或记录发送结果 | WorkBuddy 定时任务，经 MCP 转发给日程 Agent |

MCP 只负责协议适配、请求转发和结果透传；不调用后端、不执行 SQL、不承担业务规则判断。Agent 负责调用后端。

## 7. 验收标准

| 编号 | 前置条件 | 操作 | 期望结果 |
|------|----------|------|----------|
| AC-001 | 用户已完成语音输入 | 指定开始时间创建日程 | 创建成功，返回日程和提醒信息 |
| AC-002 | 用户只指定日期和时长 | 创建日程 | 系统找到空闲时间并返回实际安排时间 |
| AC-003 | 目标日期没有符合条件的空闲时间 | 创建日程 | 不创建记录，返回无可用时间原因 |
| AC-004 | 指定时间与已有日程重叠 | 创建日程 | 不创建记录，返回时间冲突 |
| AC-005 | 存在到期未发送提醒 | 定时任务轮询 | 返回该提醒，状态仍可被可靠处理 |
| AC-006 | 同一提醒被重复轮询 | 重复调用提醒查询或确认 | 不重复发送，满足幂等约束 |
| AC-007 | 提醒发送失败 | 调用确认接口 | 提醒保持待发送或失败状态，可重试 |
| AC-008 | 请求参数非法或无权限 | 调用任一能力 | 后端拒绝请求并返回稳定错误码 |

## 8. 统一接口与处理约束

- 固定链路为 `WorkBuddy → MCP → 本地 Agent → 后端 → MySQL`；MCP 不直接调用后端。
- Agent 可接入部署配置指定的 LLM 进行文本理解；空档计算、时间选择和 SQL 参数生成使用确定性逻辑。
- 单次逻辑请求最多 3 轮完整尝试；每轮可包含查询和创建。冲突后必须重新查询并修正请求，不得将查询和创建分别计为独立上限。
- 错误响应顶层必须有 `retryable`，错误对象只包含 `code`、`message`。
- 本产品为单用户自用工具，电脑和手机前端打开即可直接访问；前端页面及其调用的普通 `/api/*` 接口无需登录、密码或访问令牌。
- 服务认证仅用于 Agent 调用后端的内部接口 `POST /api/internal/sql/execute`；认证凭据由服务部署配置提供，不要求前端持有。不得通过通用 SQL 批次绕过后端业务校验；前端免认证不免除参数、业务限制和冲突校验。
- 时间按 UTC 存储，接口携带 IANA 时区；默认日程时长 30 分钟，查询范围受 `SCHEDULE_HORIZON_DAYS` 限制，提醒由 WorkBuddy 轮询、发送并确认。
- LLM 供应商由部署配置决定，契约不写死具体供应商。

## 9. 范围约束

本期包含语音创建日程、未指定时间自动排期和定时提醒。本期不要求实现自然语言之外的独立日历客户端，也不允许 Agent 或 MCP 直接访问数据库。


### T05 占用查询边界

`FIND_AVAILABLE_SLOTS` 携带 `date`、可选 `end_date`（均含当天，缺省只查目标日期）、`timezone`、`duration_min`（缺省 30）及可选 `deadline`。查询日期限定在用户时区的今天起 `SCHEDULE_HORIZON_DAYS` 个日历日内。Agent 用本地午夜边界转换后的 UTC 参数查询有效且未完成的 `scheduled_tasks`，同时按本地日期查询 `calendar_events`；后端验证两条 SELECT 的模板和绑定范围，仅返回可 JSON 序列化的占用行（ISO 日期/时间），不缓存占用查询。Agent 合并占用后按 `WORK_HOURS`、截止时间和 5 分钟粒度计算候选；查询不写库。日历事件日期/时间按请求的日历时区解释。


### 远程 MCP 接入（T11 联调准备）

WorkBuddy 云端使用 Streamable HTTP，通过 HTTPS URL 访问独立 MCP 服务的 `/mcp` 端点；本地 stdio 继续可用。HTTP 传输采用无会话模式：POST 接收单条 JSON-RPC，请求返回 `application/json`，通知和客户端响应返回 HTTP 202；不提供服务器主动推送流，GET/DELETE 返回 405，不分配 `Mcp-Session-Id`。初始化后客户端携带 `MCP-Protocol-Version`，支持 2025-03-26、2025-06-18、2025-11-25；缺省按 2025-03-26 处理。

HTTP MCP 仅做协议适配，仍经本地 Agent 调用后端。远程入口要求独立 Bearer 令牌 `SCHEDULE_MCP_HTTP_TOKEN`，不复用后端内部服务令牌；配置 `SCHEDULE_MCP_ALLOWED_ORIGINS` 校验带 Origin 的请求，无 Origin 的服务器客户端可以连接。服务默认绑定 127.0.0.1:7801，由部署提供 HTTPS 反向代理或隧道。该入口认证不改变普通前端 API 免认证的约定。真实验收仍要求 WorkBuddy 调用记录和数据库快照，本地 HTTP 测试不替代真实验收。
